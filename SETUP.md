# HD Guru — Production Setup Guide

> **Phase 8 — final integration, deployment, security, PWA and end-to-end
> verification.** This document is the single source of truth for deploying
> HD Guru. Follow it top to bottom; do not skip sections.

---

## 1. HD Guru overview

HD Guru transforms photos and videos into WhatsApp-friendly HD quality.

- **Frontend** — Next.js 15 PWA (installable, offline fallback, dynamic
  branding from the admin panel). Deployed on **Vercel**.
- **Backend** — FastAPI + SQLAlchemy + Celery media processing engine
  (image pipeline via Pillow, video pipeline via FFmpeg). Deployed on
  **Render**.
- **Storage** — S3-compatible object storage (**Cloudflare R2**), with a
  `local` driver for development.
- **Delivery** — the user taps **GET HD**, a `wa.me` link opens WhatsApp with
  `Send HD for <16-char ID>` prefilled, and the processed file is delivered
  back through the **Meta WhatsApp Business Cloud API** webhook.

## 2. Architecture

```
                    INTERNET
                       |
          +------------+------------+
          |                         |
          v                         v
       VERCEL                    RENDER
     FRONTEND                  FASTAPI API
          |                         |
          |                         +---- DATABASE (PostgreSQL)
          |                         |
          |                         +---- REDIS (Celery broker / result)
          |                         |
          |                         +---- WORKER (Celery) + BEAT (cleanup)
          |                         |
          |                         +---- R2 STORAGE (S3 API)
          |                         |
          +---- HTTPS API calls ---->+---- WHATSAPP GRAPH API

      User clicks GET HD -> wa.me opens WhatsApp
      User sends "Send HD for <ID>" -> Meta webhook -> backend
      -> DB lookup -> R2 processed media -> WhatsApp reply
```

Three communications channels (detailed in section 44):

1. **Frontend → Backend**: REST/JSON over HTTPS. Uploads, job status polling,
   result retrieval, public branding, ads config, analytics events, WhatsApp
   availability.
2. **WhatsApp → Backend**: Meta pushes events to the webhook
   (`POST /api/v1/whatsapp/webhook`), signature-verified, acknowledged
   immediately, processed asynchronously by the Celery worker.
3. **Backend → WhatsApp**: Graph API messages/media calls using the system-user
   access token.

## 5. Local development

```bash
# Backend
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows   |  source .venv/bin/activate (mac/linux)
pip install -r requirements.txt
copy .env.example .env        # then edit DATABASE_URL / JWT_SECRET_KEY
alembic upgrade head
uvicorn app.main:app --reload            # http://localhost:8000/docs

# Worker (uploads stay "queued" without it)
celery -A app.workers.celery_app.celery_app worker --loglevel=info --concurrency=4
```

Or run everything with Docker Compose (Postgres + Redis + API + worker + beat,
FFmpeg included):

```bash
cd backend
copy .env.example .env        # JWT_SECRET_KEY must be set (compose fails fast otherwise)
docker compose up --build
# Optional S3-compatible local storage:
docker compose --profile s3 up --build
```

Frontend:

```bash
cd frontend
copy .env.example .env.local  # set NEXT_PUBLIC_API_URL=http://localhost:8000
npm install
npm run dev                   # http://localhost:3000
```

Without `NEXT_PUBLIC_API_URL` the frontend runs in **demo mode** (mock data).

### Configuration management

HD Guru has **two** configuration layers. Understanding which one a value
belongs to tells you whether changing it needs a redeploy.

**ENVIRONMENT VARIABLES** → infrastructure, startup configuration, and secrets.
These are set on Render (Services → Environment) or in `.env` for local dev,
and are read once at process start. Changing them requires a redeploy/restart.

- `DATABASE_URL`, `REDIS_URL`, `CELERY_BROKER_URL`, `CELERY_RESULT_BACKEND`
- `JWT_SECRET_KEY`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`
- `STORAGE_DRIVER` + `S3_*` (R2/S3 endpoints, credentials, bucket, region)
- `MEDIA_URL_MODE`, `MEDIA_SIGNED_URL_EXPIRES`, `APP_PUBLIC_BASE_URL`
- SMTP credentials (`SMTP_*`) and other secret/key material

**ADMIN PANEL SETTINGS** → non-sensitive runtime application configuration.
These are stored in the database (`settings` table) and edited from
`Admin → Settings` (and `Admin → Ads`, `Admin → Analytics`,
`Admin → WhatsApp`, `Admin → Watermark`). They are read at request/worker
time, so changes take effect **without a redeploy**. The env vars for these
keys are only first-run fallbacks used when no DB row exists; a DB value
always wins afterwards.

- `ads.enabled`, `ads.default_provider`, `ads.default_placement_behavior`
- `analytics.enabled`, `analytics.retention_days`
- `upload.ttl_hours` (per-upload expiry), `upload.max_*`, MIME allowlist
- `rate_limit.enabled` (global rate-limit master switch)
- `watermark.enabled` (master watermark toggle)
- WhatsApp operational config: enabled, phone number ID, business account ID,
  phone number, API version, Graph base URL, and the access/verify token +
  app secret (edited from `Admin → WhatsApp → Configuration`; secrets are
  masked and never shown again)

Examples of changes that do **not** require redeployment:

- Turning ads on/off or switching the default provider
- Enabling/disabling analytics or changing retention (e.g. 30 instead of 90 days)
- Changing how long uploads live (`upload.ttl_hours`)
- Enabling/disabling watermarking
- Changing the WhatsApp number/tokens or toggling WhatsApp on/off

Things that still **do** require Render environment configuration: R2/S3
credentials, the database URL, JWT signing keys, Redis/Celery URLs, and any
other secret or infrastructure value listed above.

## 9. CORS

Configured via `CORS_ORIGINS` (comma-separated) in `backend/app/core/config.py`
(`cors_origin_list`) and applied in `backend/app/main.py`.

- **Local development**: `CORS_ORIGINS=*` (credentials are not enabled when
  `*` is present, so the middleware never combines wildcard + credentials).
- **Production**: set the exact frontend origin, e.g.
  `CORS_ORIGINS=https://hdguru.vercel.app` (add more origins comma-separated).
  Also pin `ALLOWED_HOSTS` to the backend hostname(s), e.g.
  `ALLOWED_HOSTS=hd-guru-api.onrender.com,localhost`. `*` in a production
  environment logs a startup warning (the app still boots; see §45).

## 10. Database setup

- **Production**: PostgreSQL via Render (see §28) or any Postgres provider.
  Set `DATABASE_URL=postgresql+psycopg://user:pass@host:5432/db`.
- The engine uses `pool_pre_ping`, `pool_size=10`, `max_overflow=20`
  (`app/core/database.py`). Connection pooling is handled by SQLAlchemy.
- **Do not use SQLite in production.** SQLite is for local dev/tests only.
- Health checks run `SELECT 1` (`/api/v1/health` → `database`).

## 11. Redis setup

- `REDIS_URL` (db 0): rate limiting, analytics budgets, health.
- `CELERY_BROKER_URL` (db 1): Celery broker.
- `CELERY_RESULT_BACKEND` (db 2): task results.
- Render's managed Redis service is defined in `render.yaml` (§28). The three
  URLs above point at the same instance with `/0`, `/1`, `/2` suffixes.
- If Redis is unavailable, the rate limiter falls back to an in-memory
  sliding window and health reports Redis degraded.

## 12. Celery worker

```bash
celery -A app.workers.celery_app.celery_app worker --loglevel=info --concurrency=2
```

Processes `uploads.process` and `whatsapp.process_event`. On Render it is the
`hd-guru-worker` background worker (`render.yaml`). Tasks: uploads →
`queued → analyzing → enhancing → watermarking → compressing → storing →
completed` (or `failed`).

## 13. Celery beat

```bash
celery -A app.workers.celery_app.celery_app beat --loglevel=info
```

Scheduled tasks (defined in `app/workers/celery_app.py`):

- `uploads.cleanup_expired` — **hourly**, deletes expired media rows **and**
  their R2 objects (rows are only removed after objects are gone).
- `analytics.retention_run` — **daily**, purges raw analytics/ad events older
  than `ANALYTICS_RETENTION_DAYS`.

On Render this is the `hd-guru-beat` background worker. Run exactly one beat
instance.

## 14. FFmpeg

**Do not assume FFmpeg exists on the production host.**

- **Docker (local)**: `backend/Dockerfile` installs `ffmpeg` via apt.
- **Render**: `render.Dockerfile` (built from the repo root, copies
  `backend/`) installs `ffmpeg` via apt in the image. The video pipeline
  (`app/services/processing/video_processor.py`) uses `ffprobe` + `ffmpeg` and
  refuses to run without them.
- The image pipeline (Pillow) needs no FFmpeg.

## 15. Cloudflare R2 setup

1. In the Cloudflare dashboard open **R2** and create a bucket
   (e.g. `hd-guru-media`).
2. Go to **R2 → Manage R2 API Tokens** → **Create API Token**, allow
   *Object Read & Write*, scoped to the bucket. Note the **Access Key ID** and
   **Secret Access Key** (shown once).
3. The **S3 API endpoint** for your account is
   `https://<account-id>.r2.cloudflarestorage.com` (shown on the R2 overview
   page). This is `S3_ENDPOINT_URL`.
4. Configure a **custom domain** for the bucket (R2 → bucket → Settings →
   Custom Domains) so you can serve media over HTTPS on your own domain, or
   use the bucket's `r2.dev` public URL. This is `S3_PUBLIC_BASE_URL`.

## 16. R2 bucket configuration

Set on the backend:

```
STORAGE_DRIVER=s3
S3_ENDPOINT_URL=https://<account-id>.r2.cloudflarestorage.com
S3_ACCESS_KEY_ID=<access-key-id>
S3_SECRET_ACCESS_KEY=<secret-access-key>
S3_BUCKET_NAME=hd-guru-media
S3_REGION=auto
```

`S3_FORCE_PATH_STYLE` stays `false` (R2 supports virtual-host style). Object
keys are built from the server-generated public ID — never the user filename
(`app/utils/object_keys.py`): `media/{original|processed|thumbnails}/{YYYY}/{MM}/{public_id}.ext`.

## 17. R2 public / private URL configuration

Choose one mode in `MEDIA_URL_MODE`:

- **`public`** (default): `S3_PUBLIC_BASE_URL` must be set. Media URLs are
  `https://<your-media-domain>/media/processed/2026/08/<id>.jpg`. The bucket
  (or the custom domain behind it) must be publicly readable.
- **`signed`**: the bucket can stay fully private. URLs are short-lived
  pre-signed links (`MEDIA_SIGNED_URL_EXPIRES`, default 3600 s). Use this when
  you do not want media publicly readable.

For WhatsApp delivery, Meta fetches the media URL. With `public` mode the URL
must be reachable by Meta. With `signed` mode the URL must still be valid when
Meta fetches it (3600 s is fine). If the bucket is private and you choose
`public`, WhatsApp delivery will fail with "media URL not reachable".

3. Under **WhatsApp → API Setup** you will find the **Phone number ID** and

## 19. WhatsApp Business setup

- Connect your business phone number in the Meta app (Settings → Business →
  WhatsApp). A real (non-test) number requires a Business Portfolio and, for
  messaging tiers, phone-number verification.
- Copy the business number in E.164 format (`+15551234567`) for
  `WHATSAPP_PHONE_NUMBER`.

## 20. Phone Number ID

`WHATSAPP_PHONE_NUMBER_ID` — a numeric ID, found under **WhatsApp → API
Setup**. It is part of every Graph API URL
(`/<version>/<phone-number-id>/messages`).

## 21. Business Account ID

`WHATSAPP_BUSINESS_ACCOUNT_ID` — the WhatsApp Business Account (WABA) ID,
found in **Business Manager → WhatsApp Account**. Informational for HD Guru.

## 22. Access Token

`WHATSAPP_ACCESS_TOKEN` — a **system-user token** (Business Manager → Settings
→ System Users → Generate Token) with the permissions:

- `whatsapp_business_messaging`
- `whatsapp_business_management`

Do not use a short-lived user token. Never expose this token to the frontend.

## 23. App Secret

`WHATSAPP_APP_SECRET` — from **Meta App Dashboard → App Settings → Basic**.
Used to compute the expected `X-Hub-Signature-256` on every webhook POST.

## 24. Webhook configuration

In the Meta App → **WhatsApp → Configuration → Webhook**, set:

- **Callback URL**: `https://<your-backend-host>/api/v1/whatsapp/webhook`
- **Verify token**: a secret string you choose → `WHATSAPP_VERIFY_TOKEN`

The backend's GET handshake (`app/api/v1/endpoints/whatsapp.py`) echoes
`hub.challenge` only when `hub.mode=subscribe` and the verify token matches
(constant-time compare).

## 25. Webhook URL

`https://<your-backend-host>/api/v1/whatsapp/webhook`

- `GET` → verification handshake (no auth header required).
- `POST` → event delivery; must reply `200 OK` **immediately** (the backend
  persists the event and enqueues processing asynchronously).

Meta requires the endpoint to answer `GET` (challenge) before it will POST.

## 26. WhatsApp permissions

Your access token needs `whatsapp_business_messaging` (send/receive) and
`whatsapp_business_management` (manage the WABA). The webhook subscription is
the **`messages`** field. Delivery/read statuses arrive as part of `messages`.

## 28. Render deployment

Use the committed **Render Blueprint** (`render.yaml`) — it provisions
PostgreSQL, Redis, the web API, the Celery worker and beat together.

1. Render Dashboard → **New +** → **Blueprint** → connect the repository.
2. Render reads `render.yaml` and creates:
   - `hd-guru-db` (PostgreSQL, `starter`)
   - `hd-guru-redis` (Redis, `starter`)
   - `hd-guru-api` (web; runs `alembic upgrade head && uvicorn …` on boot;
     health check `/api/v1/health`)
   - `hd-guru-worker` (Celery worker)
   - `hd-guru-beat` (Celery beat)
3. After the first deploy, open each service → **Environment** and fill the
   `sync: false` secrets (they are created empty):
   - `S3_*` (R2 credentials), `WHATSAPP_*` (tokens/secrets),
     `APP_PUBLIC_BASE_URL`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`.
   - `CORS_ORIGINS`, `ALLOWED_HOSTS`, `STORAGE_DRIVER`, `MEDIA_URL_MODE`.
   - `JWT_SECRET_KEY` is auto-generated (`generateValue: true`).
4. **Restart** `hd-guru-api` after setting secrets so the new values load.
5. Point your frontend at `https://hd-guru-api.onrender.com`.

> `$`-interpolated values (e.g. `CELERY_BROKER_URL: ${REDIS_URL}/1`) are
> resolved by Render. If a service fails to boot with a Redis URL error,
> set `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` explicitly to the managed
> Redis URL plus `/1` and `/2` in the dashboard.

### FFmpeg on Render

Installed inside `render.Dockerfile` (apt). No host install needed. Verify
after deploy: `https://<host>/api/v1/health` reports `storage: ok`, and video
uploads do not fail with "FFmpeg not found".

### Background workers

- **Worker**: `hd-guru-worker` runs `celery … worker`. Concurrency 2.
- **Beat**: `hd-guru-beat` runs `celery … beat`. Exactly one instance.
- Both share the same env vars as the API (via `render.yaml`).

### Production startup & migrations

The API's container command is `alembic upgrade head && uvicorn …`, so
migrations run automatically before the app accepts traffic on every deploy.
Never run `alembic downgrade` in production. There are no destructive
automatic operations: cleanup only deletes expired rows **after** their R2
objects are removed.

## 34. Branding configuration

Single source of truth = backend **Setting** rows, edited via
**Admin → Settings** (keys `app.name`, `app.description`, `app.logo_url`,
`app.theme_color`, `app.primary_color`, etc.).

How it reaches the public site:

- `GET /api/v1/settings/public` returns only public branding (no admin/private
  settings, no secrets).
- The frontend fetches it (`frontend/services/branding.ts`, 5-min cache) and
  applies it to the document (theme color, description, logo, title) and the
  PWA manifest (name, description, theme color) via `app/manifest.ts`.
- If branding has not been configured, the app falls back to the compiled
  HD Guru defaults. It never breaks.

**Runtime vs build-time branding values:**

| Value | Configurable at | Notes |
| --- | --- | --- |
| App name | runtime (client + manifest) | manifest is generated per-request and reads branding |
| App description | runtime (client + manifest) | same |
| Theme color | runtime (client + manifest) | manifest `theme_color` + viewport meta |
| Logo | runtime (client) | shown in header/footer via `app_logo_url` |
| PWA icons (192/512/maskable/apple) | **build-time** | static files in `frontend/public`; the manifest can serve `app_logo_url` but icon files are static |
| Favicon | **build-time** | `frontend/app/favicon.ico` |
| Primary color (CSS) | runtime (client) | sets `--brand-primary`; Tailwind utility classes are compiled at build time, so some surfaces keep the default palette |

> **Documented limitation:** PWA icons and the favicon are static build-time
> assets. To change them, replace `frontend/public/icon-192.png`,
> `icon-512.png`, `apple-touch-icon.png` and `app/favicon.ico` and redeploy.
> The manifest, name, description, theme color and in-page branding are fully
> runtime-configurable from the admin panel.

## 39. Troubleshooting

### "Frontend cannot connect to backend" / "Network Error"

- **Cause**: `NEXT_PUBLIC_API_URL` unset/wrong, or CORS misconfigured, or the
  backend is down.
- **Diagnose**: open the browser DevTools Network tab; check the failed request
  URL and response; hit `https://<api>/api/v1/health` directly.
- **Fix**: set `NEXT_PUBLIC_API_URL` on Vercel (requires redeploy); confirm the
  Render service is live; check backend logs.

### CORS error

- **Cause**: request origin not in `CORS_ORIGINS`.
- **Diagnose**: browser console shows `has been blocked by CORS policy`.
- **Fix**: add the exact frontend origin to `CORS_ORIGINS` on Render, restart
  the API. Do not use `*` with credentials in production.

### 401 Unauthorized

- **Cause**: missing/expired/invalid JWT.
- **Diagnose**: re-login; check `ACCESS_TOKEN_EXPIRE_MINUTES`; verify
  `JWT_SECRET_KEY` is stable across deploys.
- **Fix**: log in again; ensure the same `JWT_SECRET_KEY` on all services.

### 403 Forbidden

- **Cause**: role/permission missing, or TrustedHost/CSRF rejected the host.
- **Diagnose**: check which endpoint; check `ALLOWED_HOSTS`.
- **Fix**: grant the role in Admin → Users; pin `ALLOWED_HOSTS` to the real
  hostname.

### Upload fails

- **Cause**: file too large, unsupported type, or count over 5.
- **Diagnose**: response body has a friendly `error.message`.
- **Fix**: check `MAX_FILE_SIZE_MB`, `MAX_UPLOAD_SIZE_MB`, allowed MIME list.

### Processing stuck

- **Cause**: Celery worker not running, or Redis down.
- **Diagnose**: status stays `queued`; check `hd-guru-worker` logs.
- **Fix**: start/scale the worker; verify Redis connectivity.

### FFmpeg not found

- **Cause**: image deployed without FFmpeg (custom Dockerfile).
- **Diagnose**: video jobs fail; `ffmpeg -version` fails in the container.
- **Fix**: use `render.Dockerfile` (installs FFmpeg); rebuild.

### R2 upload fails / R2 access denied

- **Cause**: wrong endpoint, wrong keys, or region.
- **Diagnose**: backend logs show `STORAGE_ERROR`; test with `S3_REGION=auto`.
- **Fix**: verify `S3_ENDPOINT_URL`, key ID/secret, bucket name; ensure the
  token allows Object Read & Write.

### Media URL returns 404

- **Cause**: `MEDIA_URL_MODE=public` but `S3_PUBLIC_BASE_URL` wrong, or object
  expired/deleted.
- **Diagnose**: fetch the URL from the result payload directly.
- **Fix**: correct the public base URL; check bucket public access; re-upload.

### Signed URL expired

- **Cause**: `MEDIA_SIGNED_URL_EXPIRES` too short (default 3600 s).
- **Diagnose**: URL returns 403/expired when opened later.
- **Fix**: increase the expiry or switch to `public` mode.

### WhatsApp webhook verification failed

- **Cause**: verify token mismatch or wrong URL.
- **Diagnose**: Meta shows "Verification failed".
- **Fix**: `WHATSAPP_VERIFY_TOKEN` must match the Meta dashboard token exactly;
  the callback URL must be `…/api/v1/whatsapp/webhook` (GET handshake).

### WhatsApp webhook returns 403

- **Cause**: `X-Hub-Signature-256` mismatch → `WHATSAPP_APP_SECRET` wrong.
- **Diagnose**: backend logs "signature mismatch"; POST from curl reproduces it.
- **Fix**: set the correct app secret; keep it stable across restarts.

### WhatsApp message received but media not sent

- **Cause**: media URL not reachable by Meta (private bucket + `public` mode),
  expired signed URL, or missing token/phone number ID.
- **Diagnose**: check the worker task log for the event; test the media URL
  from a non-browser context.
- **Fix**: use `MEDIA_URL_MODE=signed` (or public bucket), confirm token +
  phone number ID, re-upload.

### Invalid HD ID

- **Cause**: the message text did not match `Send HD for <16-char ID>`.
- **Diagnose**: webhook event stored; check the parsed ID.
- **Fix**: ask the user to resend the exact prefilled message.

### Meta API token invalid

- **Cause**: token expired/revoked or missing permissions.
- **Diagnose**: `POST /api/v1/whatsapp/config/test` (admin) returns an error.
- **Fix**: regenerate the system-user token with the two WhatsApp permissions.

### Phone Number ID incorrect

- **Cause**: wrong numeric ID.
- **Diagnose**: Graph calls fail with "path does not exist".
- **Fix**: copy the ID from WhatsApp → API Setup.

### Redis unavailable

- **Cause**: Redis service down or URL wrong.
- **Diagnose**: `/api/v1/health` → `redis: unavailable`; rate limiting falls
  back to memory.
- **Fix**: verify `REDIS_URL`; restart the Redis service.

### Celery worker not processing

- **Cause**: worker not running, wrong broker URL, or queue name mismatch.
- **Diagnose**: `hd-guru-worker` logs empty; tasks stay `queued`.
- **Fix**: ensure the worker is started with `CELERY_BROKER_URL` set; restart.

### Database migration failed

- **Cause**: pending migrations or a failed revision.
- **Diagnose**: API fails to boot; `alembic current` shows behind head.
- **Fix**: fix/apply the failing revision, then `alembic upgrade head`.

### PWA not installing

- **Cause**: manifest/icon/SW missing, or served over HTTP.
- **Diagnose**: DevTools → Application → Manifest shows errors.
- **Fix**: HTTPS required; ensure manifest + 192/512 icons + registered SW.

### Logo not updating

- **Cause**: browser/backend cache, or logo URL not set.
- **Diagnose**: `GET /api/v1/settings/public` shows `app_logo_url`.
- **Fix**: set `app.logo_url` in Admin → Settings; clear the 5-minute branding
  cache (branding is cached client-side for up to 5 minutes).

### Admin settings not appearing on public site

- **Cause**: branding cache or wrong setting keys.
- **Diagnose**: check the setting row keys (`app.name`, …) and the public
  endpoint response.
- **Fix**: use the exact keys; wait out / clear the cache.

### Vercel environment variables not updating

- **Cause**: env changes require a redeploy.
- **Diagnose**: old `NEXT_PUBLIC_*` still in the bundle.
- **Fix**: set the var, then Redeploy (Vercel) — redeploy is mandatory.

### Render environment variables not updating

- **Cause**: the service needs a restart to re-read env.
- **Diagnose**: old behavior persists after saving.
- **Fix**: save the value, then **Restart** the service.

## 40. Common errors

| Error string | Meaning | Fix |
| --- | --- | --- |
| `FILE_TOO_LARGE` | File exceeds `MAX_FILE_SIZE_MB` | Raise the limit or compress locally |
| `UNSUPPORTED_FILE_TYPE` | MIME/extension not allowed | Use a listed image/video type |
| `TOO_MANY_FILES` | More than `MAX_UPLOAD_FILES` | Upload ≤5 files |
| `UPLOAD_NOT_FOUND` | Bad/expired public ID | Re-upload |
| `MEDIA_EXPIRED` | TTL elapsed | Re-upload |
| `PROCESSING_FAILED` | Pipeline error (see worker logs) | Check FFmpeg/storage |
| `WHATSAPP_UNAVAILABLE` | Integration not configured/enabled | Configure WhatsApp env/DB row |
| `INVALID_HD_ID` | WhatsApp text did not parse an ID | Resend the exact message |
| `INTERNAL_ERROR` | Unhandled exception (generic 500) | Check backend logs (request ID in `X-Request-ID`) |
| `RATE_LIMITED` (429) | Too many requests | Wait for `Retry-After` |

The API returns user-safe messages only — never Python tracebacks, database
errors, boto3 stack traces, Meta tokens, or internal filesystem paths.

## 41. Recovery procedures

1. **API down**: restart `hd-guru-api`; check the deploy logs; verify
   `alembic upgrade head` succeeded (migrations run on boot).
2. **Worker down / jobs stuck**: restart `hd-guru-worker`; confirm Redis
   connectivity; pending tasks are re-consumed from the broker.
3. **Redis down**: rate limiting degrades to in-memory; restart the Redis
   service. Workers idle until the broker returns.
4. **R2 outage**: media fetch/upload fails but the app stays up. Re-upload
   when R2 recovers; expired rows are retried by the hourly cleanup beat task.
5. **Meta webhook misconfigured**: verify token/app secret; redo the Meta
   webhook verification handshake.
6. **Data loss / schema changes**: never `alembic downgrade` in production.
   Restore from the provider's backup, then re-apply `alembic upgrade head`.
7. **Secret rotation**: generate a new value, set it in Render, restart all
   services. A rotated `JWT_SECRET_KEY` invalidates existing sessions.

## 44. Two-end communication

### Frontend → Backend (REST over HTTPS)

| Flow | Endpoint | Notes |
| --- | --- | --- |
| Upload | `POST /api/v1/uploads` | multipart, 1–5 files, returns `jobs[]` with public IDs |
| Poll status | `GET /api/v1/uploads/{id}/status` | `queued…completed/failed` |
| Get result | `GET /api/v1/uploads/{id}` | download/thumbnail/whatsapp URLs |
| Download | `GET /api/v1/uploads/{id}/file` | increments download count |
| Public branding | `GET /api/v1/settings/public` | name/logo/theme/primary |
| Ads config | `GET /api/v1/ads/config` | public placement/provider layout |
| WhatsApp avail | `GET /api/v1/public/whatsapp` | enabled + phone number |
| Analytics | `POST /api/v1/analytics/event` | hashed-IP budgeted ingest |
| Auth (admin) | `POST /api/v1/auth/login` | JWT access+refresh; refresh rotation |

**Auth/JWT**: the admin panel logs in, stores access/refresh tokens, and sends
`Authorization: Bearer <access>` on admin APIs. The **public** upload/status/
result/branding/ads endpoints need no auth (they are keyed by the random public
ID, which is the capability token). The backend validates JWT signature, `aud`,
`iss`, `exp`, `jti`, and token version; refresh tokens are single-use.

### WhatsApp → Backend (Meta webhook)

Meta POSTs to `/api/v1/whatsapp/webhook`:

1. `GET` handshake verifies `hub.mode=subscribe` + verify token.
2. `POST` events are validated with `X-Hub-Signature-256` (HMAC-SHA256 over
   the raw body using `WHATSAPP_APP_SECRET`).
3. The backend acknowledges `200` immediately, persists the event
   (idempotency via `meta_message_id`), and enqueues `whatsapp.process_event`.
4. The worker parses the message text for `Send HD for <16-char ID>`, looks
   the `MediaFile` up, checks expiry/status, fetches the latest `ProcessedMedia`,
   resolves an R2 public/signed URL (or app route), and replies.

### Backend → WhatsApp (Graph API)

`https://graph.facebook.com/<version>/<phone-number-id>/messages` with the
system-user token. Media is sent **by URL** (no in-memory buffering):
`/media` link endpoint + `image|video|document` message with the media URL.
Delivery/read/failed statuses return via the webhook and are recorded on
`whatsapp_message_statuses`.

### Media pipeline (processing job → R2 → public ID → WhatsApp)

```
Image: upload → enhance (EXIF fix, resize ≤2048, sharpen/contrast)
       → watermark (DB row, Pillow) → progressive JPEG ≤5MB
       → R2 (object key = server-generated public ID) → public ID
       → "Send HD for <ID>" → webhook → DB lookup → R2 URL → WhatsApp

Video: upload → ffprobe → scale to caps (1080×1920 / 1920×1080 / 1080×1080)
       → watermark (filter_complex) → H.264/AAC +faststart, CRF loop ≤16MB
       → R2 → public ID → WhatsApp (same as image)
```
